# Languages in the desktop client

The client in `app/` ships six languages: English, Spanish, Portuguese and
three Traditional Chinese variants — general (`zh-Hant`), Taiwan (`zh-TW`) and
Hong Kong (`zh-HK`). They live in `app/src/lang/`, are wired in
`app/src/i18n.ts`, and end up inside the image because `make app` compiles the
client into `internal/webui/assets`, which `go:embed` carries into the binary.

## The files

Two vocabularies per language, one dictionary at runtime:

| file | what it holds |
| --- | --- |
| `desk-<code>.json` | the standalone client's own strings — rail, login, file manager |
| `panel-<code>.json` | the `wr.*` and workroom keys the ported components still speak |

`en`, `es`, `pt` and `zh-Hant` are **complete** dictionaries: same keys, same
order, 218 desk keys and 1371 panel keys each.

`zh-TW` and `zh-HK` are **not** complete, on purpose. Traditional Chinese is
one written language with regional vocabulary, so those two files carry only
the strings the regions say differently and inherit everything else:

```
zh-TW ─┐
       ├─→ zh-Hant ─→ en
zh-HK ─┘
```

The base `zh-Hant` follows the traditional standard as written in Taiwan, so
`zh-TW` is mostly a pin: it states the Taiwanese wording explicitly for the
same keys `zh-HK` overrides, which keeps the pair auditable side by side and
stops a future edit to the base from silently changing what Taiwan reads.

The divergences currently covered — 42 strings in each variant (10 desk, 32
panel), plus each file's own `_name`:

| general (`zh-Hant`, Taiwan) | Hong Kong (`zh-HK`) | meaning |
| --- | --- | --- |
| 品質 | 質素 | quality |
| 帳號 | 帳戶 | account |
| 網路 | 網絡 | network |
| 行程 | 程序 | process |
| 點一下 / 點擊 | 按一下 | click |
| 螢幕擷圖 / 擷取 | 螢幕截圖 / 截取 | screenshot / capture |
| 視訊 | 視像 | video |

## Adding a term or a language

*A new regional term*: add the key to `desk-zh-HK.json` (or the panel file) with
the Hong Kong wording, and add the same key to the `zh-TW` file with the
Taiwanese wording. Never let a variant file hold a string that is identical to
the base — that is what the fallback is for.

*A whole new language*: drop `desk-<code>.json` and `panel-<code>.json` next to
the others with the **same keys in the same order** as the English files, then
add the import, the `resources` entry and one row in `LANGUAGES` in
`app/src/i18n.ts`. The rail menu, the code chip and the browser-language
detection all read that array — there is no second list to update.

Parity check before you build:

```bash
cd app && python3 - <<'PY'
import json
for base in ('desk', 'panel'):
    en = json.load(open(f'src/lang/{base}-en.json'))
    for code in ('es', 'pt', 'zh-Hant'):
        d = json.load(open(f'src/lang/{base}-{code}.json'))
        assert list(d) == list(en), f'{base}-{code}: keys differ from English'
    for code in ('zh-TW', 'zh-HK'):
        d = json.load(open(f'src/lang/{base}-{code}.json'))
        extra = set(d) - set(en) - {'_name'}
        assert not extra, f'{base}-{code}: keys not in English: {extra}'
print('ok')
PY
```

## Which language a browser gets

`localStorage['sentineldesk.lang']` wins if it names a language that still
exists; otherwise the browser's tag decides. Chinese arrives in more shapes
than any other tag, so it is read by parts rather than by prefix:

| `navigator.language` | lands on |
| --- | --- |
| `zh-TW`, `zh-Hant-TW` | `zh-TW` |
| `zh-HK`, `zh-MO`, `zh-Hant-HK` | `zh-HK` |
| `zh`, `zh-Hant`, `zh-CN`, `zh-Hans` | `zh-Hant` |
| anything else | its two-letter code, or `en` |

Simplified Chinese has no dictionary of its own yet, so it lands on
Traditional rather than dropping the reader into English.

The docs site under `docs/guide/` is a separate dictionary (`docs.js`,
`content/<lang>.html`) and is still English/Spanish/Portuguese only. The rail's
Docs button passes `?lang=<code>`; an unknown code is ignored there and the
site picks its own default.

## Building the image with the new languages

Nothing about the language pack is special — it is compiled into the client, so
the ordinary build produces it:

```bash
make app       # vite build → internal/webui/assets (needs node)
make image     # lite + full, version stamped in
```

`make image` runs `_version` first, which bumps `version.txt` and prints the
tag it is using. It builds both variants and tags them:

- `sentineldesk:<version>-lite`, also `:latest` and `:lite`
- `sentineldesk:<version>-full`, also `:full`

`make image-lite` builds only the lite variant when the full one is not needed.
Run it and check the result:

```bash
make image-lite
make up            # image + compose up -d
make logs          # follow the desktop
```

Then open the client, use the globe button on the rail and pick 繁體中文,
繁體中文（台灣）or 繁體中文（香港）. The chip next to the label shows 繁,
繁臺 or 繁港 — a two-letter code is unreadable for these, so the variants name
themselves in their own script.

To publish, `make push` builds multi-arch (`linux/amd64,linux/arm64`) and
pushes to `$(REGISTRY_IMAGE)`.
