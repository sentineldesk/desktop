SentinelDesk

A collaborative operating system for people and AI agents. One Linux desktop, in a container, that both of them drive — seeing the same screen, taking turns, and reading each other's errors.

The second half of that is not a metaphor for an API. It is the same X display, the same session, the same room:

  • The agent is a participant, not a background process. It has a name in the list and a pointer on screen in its own colour, so it is never ambiguous whether a colleague or the model just moved the mouse.
  • They take turns. Control is claimed, never assumed — by anybody, agent included, and whether or not somebody is watching. Nobody holds the controls until they ask, so joining to watch does not hand you a desktop you did not want. When somebody is driving, asking puts a prompt on their screen and no answer means no.
  • They read the same state. Every command run in a terminal reports its exit status, whoever ran it, so a person can hit an error and ask the agent to look at what actually happened.
  • One capture, many observers. The desktop is encoded once and fanned out: to every browser, to the recorder, to a live stream. A second participant costs bandwidth, not CPU.

People drive it through a control layer in the browser. The agent drives it through a local socket with 134 MCP tools. Neither is a guest of the other.

What it is built on

A single Go binary. GStreamer runs inside the process through go-gst rather than as a child of it, so the encoder stays reachable at runtime — bitrate follows the network, keyframes answer a request, and an external destination attaches without stopping anything.

Installing and running it

It is two containers — the desktop, and the agent beside it — joined by a single volume of Unix sockets and started together with Docker Compose. There is nothing to install on the machines that connect to it: a browser is the client.

The agent is optional and the desktop does not depend on it. Naming the desktop is how you leave it out.

What you need

  • Docker with Compose v2. Docker Desktop on macOS and Windows, Docker Engine on Linux.
  • 2 GB of RAM and two cores for a comfortable 1080p30. A GPU is optional and changes a lot — see Hardware acceleration.
  • amd64 for Steam and Wine, which are in the full image only. Everything else runs on arm64 too, in both images.

Ways to start it

The one-command way, on a VPS, a Raspberry Pi or any Linux host. It installs Docker if it is missing, pulls the published image from Docker Hub, and starts the desktop in the background — nothing to clone, nothing to build.

curl -fsSL https://raw.githubusercontent.com/sentineldesk/desktop/main/install.sh | sudo bash

Add --full for the heavier image, --pass <p> to set the password, and --ip <addr> on a public VPS so the video is reachable. --help lists every option.

The published images, two services, one command. Download the file and bring it up — no clone, no build:

curl -fsSLO https://raw.githubusercontent.com/sentineldesk/desktop/main/docker-compose.yml
AUTH_PASS=change-me HOST_IP=192.168.0.100 docker compose up -d

HOST_IP is the address browsers reach this host at — its LAN address, or the public IP on a VPS. Off localhost it is required rather than optional: WebRTC would otherwise advertise the container's bridge address, which no other machine can reach, and the page stalls at “Establishing WebRTC” with the video black. Then open https://192.168.0.100:8080.

Set SENTINELDESK_TAG=full for the heavier image.

What it starts

servicecontainerwhat it is

The agent is optional, and naming the desktop is how you say so:

docker compose up -d                # the desktop and an agent beside it
docker compose up -d sentineldesk   # the desktop, on its own

The desktop has no depends_on and no link to the agent, so the second line is a complete deployment rather than a crippled one. Order does not matter either: started first, the agent waits for the desktop and reconnects when it comes back.

How the two are joined

One volume, sentineldesk-run, holding Unix sockets and mounted in both. That is the only link between them. The agent has no ports and no network of its own, so nothing about the conversation leaves the host — and the agent can only ever do what that socket grants, which is why there is one security boundary here rather than two.

volumeholds

sentineldesk-auditthe action log — kept apart, so wiping a profile never takes the record with it
sentineldesk-agentthe agent's model choice, keys and history
sentineldesk-workscratch space for screenshots and recordings in flight

Everyday commands

docker compose ps                      # what is up
docker compose logs -f sentineldesk    # follow the desktop
docker compose logs -f agent           # follow the agent
docker compose restart agent           # restart one service
docker compose down                    # stop both, keep the volumes
docker compose pull && docker compose up -d    # upgrade in place

down leaves the volumes alone, so the home, the audit log and the agent's keys survive it. To start genuinely fresh, remove them by name — and read that as the destructive command it is: docker volume rm sentineldesk-home sentineldesk-agent.

Configuring it

Compose reads a .env beside the file, which is the tidier place for anything you would otherwise repeat on the command line:

AUTH_USER=admin
AUTH_PASS=a-real-password
HOST_IP=192.168.0.100
SENTINELDESK_TAG=latest        # or `full`
TZ=America/Argentina/Buenos_Aires
KEYBOARD_LAYOUT=latam
HTTP_PORT=8080

Every one has a default; only AUTH_PASS and HOST_IP really want setting before anybody else can reach the deployment.

HTTPS is the default

The desktop serves TLS out of the box: with nothing configured it generates a self-signed certificate once, keeps it in the home volume, and the browser asks you to accept it exactly once. Your own certificate wins via TLS_CERT/TLS_KEY. This is more than the lock icon: browsers only allow the microphone and the rich clipboard on secure origins, so a desktop reached over plain HTTP was quietly missing features.

To terminate TLS yourself with a reverse proxy in front — nginx, Caddy, Nginx Proxy Manager — set TLS_SELFSIGNED=0 so the backend speaks plain HTTP to the proxy.

A relay for hostile networks

Peer-to-peer fails on symmetric NAT and where UDP is dropped. A TURN service is in the file and off by default, because a relay carries every frame of every session through it and paying that when nobody needs it is the wrong trade:

docker compose --profile turn up -d

Set CLIENT_TURN_URLS on the desktop when it is running, or browsers are never told the relay exists.

The built-in VPN

The desktop can dial OpenVPN, which needs a tunnel device and the capability to configure routes. Both are commented out in the compose file — uncomment cap_add: NET_ADMIN and devices: /dev/net/tun on the sentineldesk service. NET_ADMIN lets the container manage its own network stack, which is a real grant, so leave it off on a deployment that will never dial one.

Where seccomp=unconfined went

Earlier versions of this page passed --security-opt seccomp=unconfined, and the compose files set it too. Neither does any more. It was there for Steam, whose bootstrap needs user namespaces that Docker's default profile blocks, and Steam is only in the full image on amd64. It widens what the container may ask of the kernel, which is not a thing to leave switched on for a feature most installations never start.

It has one other effect worth knowing, in the opposite direction: with it, Chromium keeps its own sandbox. The container tests for user namespaces at startup and adds --no-sandbox only when they are missing, so the default is an unsandboxed browser — as it always was. Neither the DevTools protocol nor the accessibility tree changes either way, so the browser_* and ui_* tools behave the same.

To change the code — the contributor path. The image is built from the repository root so the Dockerfile can reach both the Go sources and the desktop assets.

# a fast type check on the host, no container involved
go build ./...
# build both variants
make image
# or just one of them
make image-lite
make image-full
# or, without make — note the --target
docker build -f deploy/Dockerfile --target desktop -t sentineldesk:latest .

--target desktop is not optional. The Dockerfile's last stage is full, so leaving it out builds LibreOffice, Firefox, GIMP, Wireshark and the rest — around 2.5 GB — and then tags that as sentineldesk:latest, a name that means lite everywhere else.

The web interface is embedded with go:embed, so editing anything under internal/webui/assets/ means rebuilding the image — the change does not appear by reloading the page.

The first run

Open https://localhost:8080 (self-signed — accept the browser's warning once). With AUTH_USER and AUTH_PASS set it asks for a login; without them it is open.

# follow the desktop's logs
docker logs -f sentineldesk
# a root shell inside the running container
docker exec -it -u root sentineldesk bash
# stop and remove it (the home volume is kept)
docker rm -f sentineldesk

From a source checkout the same three are make logs, make shell and make down.

The desktop keeps its home in a named volume, sentineldesk-home, so browser profiles, installed applications and the Steam library survive a restart or a rebuild.

Before putting it on the internet

Set AUTH_USER, AUTH_PASS and a fixed AUTH_SECRET, and serve it over TLS. See Production.

The resolution is not the binary's to change

DISPLAY_WIDTH and DISPLAY_HEIGHT are read by Xvfb when it starts, not by the server. That is why the desktop can be resized smaller at runtime but never larger than what was reserved at boot — and why changing them means restarting the container.

Command-line flags

The binary takes nine. Five are about the AI side; the other four make the binary its own distribution. Everything else is an environment variable, because everything else is configuration of a service rather than a choice made per invocation.

FlagDescription
-mcp-sock <path>The Unix socket the MCP server listens on. Empty means the MCP server does not start at all. Defaults to MCP_SOCK
-mcp-stdioRun as the stdio bridge instead of as the desktop: it connects to -mcp-sock and relays JSON-RPC between the AI host's stdin/stdout and that socket
-mcp-policy <level>full, safe or readonly — for this bridge only

The last three restrict one connection, on top of whatever MCP_POLICY already allows. A bridge can narrow itself but never widen — which is what makes it safe to hand one agent a read-only endpoint without changing anything for anyone else:

docker exec -i -u sentineldesk sentineldesk \
  /usr/local/bin/sentineldesk -mcp-stdio \
  -mcp-sock /run/user/1000/sentineldesk-mcp.sock \
  -mcp-policy safe -mcp-deny 'ssh_*,install_packages'

Hardware acceleration

The encoder is chosen at startup by running a real probe pipeline for each candidate in turn, so what you get reflects what actually works on that host rather than what the drivers claim. Force one with ENCODER=nvenc|vaapi|h264|vp8.

To use a GPU, pass the device into the container. For VA-API add --device /dev/dri and the probe picks it by itself. NVENC needs the NVIDIA Container Toolkit and --gpus all; without a usable GPU the desktop falls back to software encoding.

Why x264 and not VP8 without a GPU

Measured on desktop content, libx264 at veryfast carries 1080p for roughly a third of what vp8enc needs, and H.264 is what every browser decodes in hardware. That matters on the receiving side too: a client that cannot keep up looks like a congested network to the congestion estimator, and drags the whole room's bitrate down.

Production

The security model

It is short enough to state in one line: the WebSocket is the only door.

The first WebSocket frame has to be an authentication frame with a username and password, or a session token. Until it validates there is no WebRTC handshake at all — no SDP offer, no ICE, no DataChannel. An invalid token, an offer trying to skip authentication, or silence past the ten-second deadline closes the connection.

Repeated failures from one origin are rate-limited and then banned for a while, so a password is not something that can be guessed at speed.

  • Set AUTH_SECRET to a fixed value. Left unset it is random, and every restart invalidates everyone's session.
  • FILES_ROOT bounds what the file manager can reach. Leave it inside the home unless you mean otherwise.
  • Downloads travel with a one-time ticket in the URL rather than the session token, so a link that leaks is already spent.
  • The MCP socket is 0600 and local to the container. It is never exposed over the network.

TLS

The desktop serves HTTPS itself. With nothing set it generates a self-signed certificate on first start and keeps it in the home volume; TLS_HOSTS puts the right names on it. To use your own, pass TLS_CERT and TLS_KEY (one without the other refuses to start). To terminate TLS in a reverse proxy in front — nginx, Caddy — set TLS_SELFSIGNED=0 so the backend speaks plain HTTP to the proxy. Either way the client switches to wss:// on its own. This matters beyond the lock icon: the microphone and the rich clipboard only work on a secure origin.

Ports and NAT

PortProtocolWhat for
8080TCPThe web interface and the WebSocket
3478UDPThe embedded STUN responder
59000–59049UDPWebRTC media — pin the range with WEBRTC_MIN_PORT / WEBRTC_MAX_PORT

If the host sits behind NAT and does not hold its reachable address on its own interface — a cloud VPS, or Docker on a VM — set NAT1TO1_IP to that address (its LAN or public IP) so WebRTC advertises something a browser can reach. Without it the browser is handed the container's bridge address and the video connects and stays black.

TURN on macOS and Windows

Docker Desktop runs the container inside a VM, so the addresses ICE discovers are the VM's and not reachable, and a direct connection may not form. A TURN relay closes that gap — point the browser at one with CLIENT_TURN_URLS (and TURN_USER / TURN_PASS). On a Linux host with the ports above published, none of this is needed.

Updating and state

Rebuilding replaces the image; it does not touch the home.

git pull
make up

What survives lives in the named volume sentineldesk-home: browser profiles, applications you installed, the Steam library, the self-signed certificate. What does not is anything written outside the home inside the container — that goes with the old image.

To start over, and lose all of it:

make down
docker volume rm sentineldesk-home
A rebuilt image but the old interface

That should not happen: the client is served with an ETag over its own bytes, so the browser has to revalidate. If it does, confirm the container was recreated rather than restarted — make up rebuilds and recreates.

The control layer

Everything you operate lives in a rail on the left of the browser window. It floats over live video of a real desktop, so it is deliberately frosted rather than solid: what it covers is desktop you stop seeing.

Press º to show and hide it. That key never reaches the remote desktop.

GroupWhat is in it

Windows of this layer — the file manager, statistics, streaming — stay open while you use the rail, can be dragged by their title bar, and close only from their own ×. Double-clicking the title bar re-centres one that ended up somewhere awkward.

Sharing the session

One desktop, several participants. The model is a shared console: exactly one participant holds control at a time and everyone else watches. The capture is encoded once and sent to all of them, so a second viewer costs bandwidth, not CPU.

Taking and releasing control

The presence panel at the top of the rail says which of three states you are in: you are driving, somebody else is, or nobody is. Control is cooperative between people — anyone may take it, and whoever had it sees the change immediately. There is no hierarchy, because everyone got in with the same credential.

Joining does not give you the controls. The desktop starts with nobody driving and stays that way until somebody asks, so opening it to watch a colleague work is a thing you can do without taking the machine out from under them. Press Take control when you actually want it.

Releasing frees the controls; it does not hand them to the next person. "I have finished" and "you are up now" are different statements, and only the first one is ever true. The same holds if the person driving simply closes their tab: the controls go free rather than landing on whoever happens to have been there longest.

The floating bar

A bar at the bottom of the screen tells everyone which way things stand, and it carries the button: green when the controls are free, amber when somebody else is driving. It stays for as long as that is true instead of flashing past — the moment the agent finishes a task is exactly when you might be looking somewhere else.

Who is who: inks and pointers

Every participant gets a colour on arrival — yellow first, then cyan, magenta and near-black — and violet always means the AI agent, never a person. The roster's dots wear it, and so does the pointer: while you are watching, your mouse over the desktop is drawn there for everyone else, named and in your ink, so pointing at things works without taking the controls. Recordings and outbound streams include those pointers, because they are drawn on the desktop itself.

The AI agent's turn

The agent is a participant like any other: a name in the list and a pointer on screen in its own colour, so it is never ambiguous whether a colleague or the model just moved the mouse.

The rule is one line: control is claimed, never assumed. That holds for the agent whether or not anybody is watching — an empty room used to be a free pass, and it is not one any more. Asking costs the agent nothing when the controls are free, because the answer comes back immediately; what it buys is a room that always knows who has the desktop. When somebody IS driving, the agent has to ask them — a prompt appears on your screen with a draining timer, and no answer means no.

Reading each other's errors

Every command run in a terminal on this desktop reports its exit status, whoever ran it. So a person can hit an error, ask the agent to look at it, and the agent reads what actually happened instead of being told about it second-hand.

Talking to the agent from the browser

The round button at the top of the rail opens a chat beside the desktop: the screen splits, the desktop on the left and the conversation on the right. You ask for something in your own words, the agent works, and you watch it while it happens — every tool it calls appears under its reply, lined up with whatever is moving on the screen next to it.

The dot on the button says whether there is anything to talk to before you press it: green ready, amber running but with no model configured, grey not there.

You need the agent

The desktop works on its own; the agent is optional and lives in its own repository. The panel tells three situations apart and offers the command that fixes each one — not installed, installed but not running, or running with no model. Copy the line, run it, and the panel goes green by itself: nothing to reload.

The desktop never depends on it

An agent that is missing, an API key that expired, a loop that will not terminate: each costs the chat panel and nothing else. The desktop boots the same, the session carries on, and restarting the agent touches neither the video nor anyone watching it. AGENT_ENABLED=0 turns the whole plane off.

It works automatically, and still asks for the controls

From the chat the agent acts without asking about each step — that is what it is for. What does not change is the desktop's own rule: if you are driving, it has to ask you, with the same card as always. And when it decides to check something with you before doing it, it asks in the chat, where you are looking.

One history

The panel's conversations and the terminal's are the same conversations: they are kept in one database and the history button reads that one. A task you started by typing in the terminal shows up in the browser, and the other way round.

Screenshots and recording

Both are in the Capture group, and both go through the server rather than the browser. That means the file comes out at the framebuffer's own quality, without the stream's compression — and as MP4, which opens on any operating system with nothing installed. WebM and MKV are available too.

Other participants' pointers are drawn onto the X display itself, so they appear in screenshots and recordings the same way they appear on screen.

Streaming the desktop out

Stream out in the Capture group sends the live session somewhere else: YouTube, Twitch or Facebook with just a stream key, or a full address for a VLC or OBS you run yourself.

It reuses the encode the room is already producing. Going live does not interrupt what anyone is watching, and an extra destination costs a muxer and a socket rather than a second capture of the screen. The multiplier that is real is bandwidth: each destination carries the full stream out of the machine.

Whoever holds control decides, and everyone in the room sees the destination list — a session being broadcast is not something to find out about afterwards. Stream keys are redacted before they reach any browser or log.

YouTube, Twitch, Facebook

Pick the platform and paste only the stream key. The ingest address is already known, so there is nothing to look up.

Watching it in VLC

Two steps, in this order: start VLC listening first, then press Go live. If nothing is listening, the desktop has nowhere to send to.

"C:\Program Files\VideoLAN\VLC\vlc.exe" ^
  --network-caching=200 "udp://@:5000"

The @ is what makes VLC listen instead of connect — without it, nothing happens and no error is printed. --network-caching=200 drops VLC's own buffer from one second to 200 ms; leave it out and you will blame the streaming for a delay that is VLC's.

You can check it really is listening:

# Linux / macOS — should show UDP *:5000, not a random high port
lsof -nP -iUDP:5000

Step 2 — in the rail, choose VLC / OBS and enter the address:

Where Docker runsAddress to use
Docker Desktop, same machine as VLC (macOS, Windows) udp://host.docker.internal:5000
Docker on Linux, same machine as VLC udp://172.17.0.1:5000
A different machine udp://<that machine's IP>:5000

Leave Viewers can join mid-stream unchecked. It is your own receiver — it does not need a keyframe every two seconds, and the bits saved go back into keeping text readable.

Why udp:// and not srt:// for VLC

VLC 3 speaks SRT only as a caller: it can connect out, but it cannot receive a connection, and ?mode=listener is silently ignored. Point SentinelDesk at it over SRT and both sides end up calling, neither answers, and nothing is logged because nothing failed. Use udp:// for VLC.

Watching it in OBS

Add a Media Source, untick Local File, and put the same udp://@:5000 in the input box. OBS is happy with srt:// too, in listener mode.

Which protocol to use

SchemeUse it for
udp://A player on your network. Works everywhere, nothing to negotiate.
srt://A receiver over the internet that listens: an SRT server, OBS in listener mode. Recovers from packet loss; pointless on a LAN.
rtmp://, rtmps://The platforms. Elderly and awkward, and the only thing they accept.

About keyframes

A viewer cannot see anything until a keyframe arrives, so a platform serving an audience that turns up at arbitrary moments needs one every two seconds. That is enforced automatically while such a destination is connected, and it goes back to on-demand the moment the last one stops.

Keyframes are ten to fifty times the size of a normal frame, and every bit they take is a bit not spent on the text on your screen. A receiver you start yourself can simply wait for the first one, which is why it gets a sharper picture.

H.264 only

No streaming destination accepts VP8. Encoder auto-detection prefers x264 over VP8, so this is normally already true; on a host where it is not, set ENCODER=x264.

The address is remembered

What you type is kept in this browser, per destination, so reopening the panel mid-stream shows what is being sent and stopping does not mean pasting a stream key again. It is stored the way a browser stores a password: on this machine, for this site, and nowhere else.

Moving files

Files in the Session group opens a two-pane manager: the remote desktop on the left, your own machine on the right. Function keys along the bottom do the usual things — F5 copy, F6 rename, F7 new folder, F8 delete, F2 refresh.

You can also drop files anywhere on the page to send them to the desktop, without opening the manager at all.

Downloads travel with a one-time ticket in the URL rather than your session token, so a link that leaks is spent and useless. FILES_ROOT bounds what the manager can reach.

Your microphone, on the desktop

Microphone in the Capture group sends your microphone into the container, where applications see it as a real input device — not as a monitor of something playing, which browsers hide from their microphone pickers. Which one it uses is chosen in Settings — the gear in the rail, or a right-click on the button.

Only the participant holding control may publish audio. Your voice becomes part of the desktop: applications, recordings and outgoing streams all hear it. For talking with the other people in the room without the desktop hearing a word, see Voice.

Voice, among the people watching

Voice in the Session group is the other conversation: a voice conference among the people in the room, browser to browser. The desktop never hears it — recordings, outgoing streams and the applications inside carry no trace of it. Picture four people narrating a video that plays on the shared screen: the commentary is Voice; the video's own sound stays on the desktop.

It is opt-in per person, like a walkie-talkie: pressing your own button captures your microphone and announces you, and switches nobody else on. Whoever else has Voice active connects to you directly, peer to peer — the audio travels between browsers, and the server only relays the sealed handshake envelopes without reading them. With three or four people it is a mesh: every pair holds its own connection, everyone hears everyone.

Alone in the conference nothing sounds: the counter on the button shows how many peers are connected, and 0 is a waiting state, not a fault. Order does not matter either — whoever activates Voice later announces themselves and the pairs form on their own. Pressing the button again leaves the conference and releases your microphone.

Which device each conversation uses — the desktop's microphone and the conference's — is chosen in Settings, where a level meter and a self-listen test answer "does this one hear me" before anybody else has to. Voice needs no control and no turn: watching is enough. It is the conversation about the desktop, not with it.

Settings: your devices and your name

The gear in the Session group — or a right-click on Microphone — opens Settings. It answers the two questions every call ends up asking: which device, and does it hear me.

Microphone and Voice are chosen separately, because they are different acts — the desktop's own input and the viewers' conference — and somebody with a headset and a desk mic genuinely wants them apart. The level meter follows whichever picker you touched last; Hear myself loops your own voice to the chosen output (headphones are kinder), and the speaker test plays a chime on the output you picked. Choices are remembered per browser and take effect immediately, even mid-session.

Your name lives here too: letters, digits, space, dash and underscore. It shows in the roster, in the session's audit record, and on the pointer tag the others see — set it once and the room stops calling you "Viewer 2".

The on-screen keyboard

Keyboard in the Viewer group docks a full board at the bottom of the screen — made for tablets, useful anywhere. Two layouts (ES, Spanish ISO with ñ, ç and the dead keys; EN, US ANSI), a numeric pad and navigation cluster behind the 123 switch, and a compact Mini variant. The — button tucks the board into a small pill at the bottom centre; tap the pill to bring it back.

Accents compose the way a phone keyboard does: tap ´ and then a vowel and one á arrives — tap the accent twice for the literal character. Shift, Ctrl, Alt and AltGr are latches: tap one, tap a key, and the chord travels. The monitor key is this desktop's ⊞ — one tap opens the applications menu.

On a touch screen the desktop itself is direct manipulation: one finger is the pointer with the left button held, two fingers scroll, and a quick two-finger tap is the right button.

With the board open, a real keyboard lights its own keys on it as you type — the same red a touch press shows. It is a live "this is how I write", and it confirms at a glance that the keys are landing.

The browser's own AI can drive it

Beyond the agent that connects over MCP, the desktop offers a set of tools to whatever AI the browser itself carries — the emerging "model context" API that Chrome's built-in Gemini reads. Nothing to install and no key to paste: from the moment you are signed in and connected, the page publishes its tools, and the browser's model can act through them.

The tools do exactly what you do, over exactly your path: type, press keys, move and click the pointer, scroll, set the clipboard, take a screenshot, list and organise files, set the quality, take or release the controls. They travel the authenticated DataChannel your own clicks take — no separate endpoint, no second login. So the browser's AI reaches exactly as far as you can and no further: anything that writes to the desktop waits until the controls are held, and asks the model to take them first.

The tools appear when the session is live and disappear when it ends.

The AI agent

SentinelDesk exposes 134 tools over a local Unix socket using the Model Context Protocol. An AI host — Claude Code, Claude Desktop, or anything else that speaks MCP — connects through a thin bridge:

docker exec -i sentineldesk sentineldesk -mcp-stdio

Killing the AI host does not take the desktop down with it. The socket is 0600 and local to the container.

Connecting one

The bridge is a sub-command of the same binary, run through docker exec. In your MCP client's configuration:

{
  "mcpServers": {
    "sentineldesk": {
      "command": "docker",
      "args": [
        "exec", "-i", "-u", "sentineldesk", "sentineldesk",
        "/usr/local/bin/sentineldesk", "-mcp-stdio",
        "-mcp-sock", "/run/user/1000/sentineldesk-mcp.sock"
      ]
    }
  }
}

-i keeps stdin open, which is the transport; -u sentineldesk runs as the socket's owner.

The tools cover the mouse and keyboard, windows, running commands, screenshots and recording, the browser through DevTools, the accessibility tree — so the agent can read what is on screen as structure rather than as pixels — files, packages, SSH, and the room itself.

Finding the right tool

A hundred and twenty tool descriptions is a real amount of a model's attention, spent before it has read your request. tool_search is the way around it: describe the task and get back the handful of tools that do it, with their input schemas attached so they can be called straight away.

{"name": "tool_search", "arguments": {"query": "give someone remote access"}}

That returns the ssh_* tools, ranked, each with its risk level and its schema. Ask for a whole theme instead with {"category": "ssh"} — the themes are ssh, shell, terminal, browser, accessibility, windows, input, screen, files, processes, packages, snapshot, recording, restream, room, audio, clipboard, desktops, system and general.

Searching only saves anything if something is not being listed in the first place, and most AI hosts already handle that themselves — Claude Code defers tool schemas and loads them on demand. For hosts that do not, set MCP_DISCOVERY=1: the tool list then advertises a core set of twelve — enough to look at the desktop, read its structure, click, type and run something — and leaves tool_search to surface the rest.

Every other tool stays callable. Discovery narrows what is advertised, never what is permitted; that is the policy's job, below. A tool left out of the list is one the agent has not been told about yet, not one it is forbidden to use.

Limiting what it may do

Every tool declares what it can do to the machine, and the policy levels are built on that one declaration:

RiskWhat it meansExample
readObserves; changes nothing screenshot, ui_tree
writeDrives the desktop — input, windows, volume, the clipboard — but cannot reach the system underneath mouse_click, type_text
dangerRuns code, touches the system, or moves data outwardrun_command, ssh_exec
VariableEffect
MCP_POLICY=fullEverything (default)
MCP_POLICY=approveThe danger tools wait for a person in the room to allow each call — a prompt with the tool and its arguments, Allow / Deny; nobody present means no
MCP_POLICY=safeRemoves the danger tools — those that run code or touch the system
MCP_POLICY=readonlyOnly the read tools
MCP_DENY / MCP_ALLOWPatterns, for finer control
MCP_DISCOVERY=1Advertise only the core set and let tool_search find the rest. Not a permission — see above

A connection may restrict itself further, but never widen — which is what makes it safe to hand an agent a read-only endpoint without changing anyone else's.

The risk levels are also published as the Model Context Protocol's own readOnlyHint and destructiveHint annotations, so an AI host that understands them can decide on its own when to ask you before acting — without knowing anything about SentinelDesk.

The TUI: driving the agent from a terminal

The chat panel in the browser is one face on the agent. The other is a terminal session, and it is the one with everything in it — the model picker, the cost panel, the approval prompts. Open it in the agent's container:

docker exec -it sentineldesk-agent sentineldesk-agent

With no arguments it finds the socket, opens a session, and waits. Each task you type keeps the previous one's context, so it is a conversation rather than a series of unrelated questions. The two faces are views of the same session: what you do here shows up in the browser panel.

What you can type

Anything that is not a slash command is sent to the agent — as a new task, or as steering if one is already running. Typing / opens a palette that completes as you go, so none of these has to be memorised.

command
/helpwhat you can type here
/modelpick the model that answers next — switches mid-session, no restart
/connectadd a provider's API key, checked with the provider before it is saved
/panel · ctrl+bthe session's context, tokens and cost so far
/compactfold the older conversation into a summary
/rewind · /undodrop back before an earlier task — the desktop is not rewound
/memoryhave something remembered, permanently
/stop · ctrl-cend the run after this turn
/languagethe language of the interface
/exit · ctrl-dleave the session

Commands your deployment shipped in commands/*.md appear in the palette too — a command is a stored prompt with a name, so typing one expands to its text exactly as if you had written it out.

/rewind moves the conversation, not the machine

It drops the transcript back to before an earlier task, which is the cheap way out of a model that went down a wrong path five turns ago. What it cannot do is undo what was done: packages are still installed, windows are still open, files are still written. The agent is told so in the same breath, and the audit trail is append-only and is not rewound — what happened happened. For a real undo of the machine, take a restore point first with snapshot_create.

Approving what it does

Start with -mode ask and every call that changes something stops for you first. Reads go through untouched, deliberately: a confirmation for every screenshot trains somebody to press y without reading, and a confirmation nobody reads is worse than none.

docker exec -it sentineldesk-agent sentineldesk-agent -mode ask
key
yallow this call
nrefuse it — the agent is told not to look for another way round
aallow calls like this one for the rest of the run
tallow this tool for the rest of the run, whatever the arguments

a binds to the command's human-understandable name, so approving apt install nginx also covers apt install curl and does not cover rm. A chained or redirecting command is never generalised: approving apt update cannot become approval for apt update && rm -rf /.

Grants live for the run and never reach disk — one that outlived the session would outlive the reason somebody gave it. Every grant, and every later call that used one, is written to the trail, so “why wasn't I asked?” is answerable afterwards.

Bounding a run

All four are off by default and compose freely:

sentineldesk-agent -run "install nginx and show me it working" \
  -max-turns 40 -max-spend 0.50 -max-time 10m -mode ask

-max-turns is a checkpoint rather than a wall: reaching it asks the model whether more steps would finish the job, and there is a hard ceiling behind that it cannot argue past. -max-spend and -max-time are ceilings — they end the run with what it has, they do not make it hurry.

Reading back what happened

The trail is the point of the whole design, and these are how you read it:

sentineldesk-agent -history          # every past run, with turns, calls and cost
sentineldesk-agent -history 42       # one run in full
sentineldesk-agent -export 42        # the whole session on stdout
sentineldesk-agent -costs            # what has been spent, and on what
sentineldesk-agent -resume 42        # pick it back up; 0 is the most recent

-history <id> shows the model's own plan beside what it actually did, names which agent acted when a sub-task was delegated, and says plainly why a run stopped — blocked · over-budget, rather than leaving you to infer it from a turn count that happens to equal the limit.

-resume redraws the conversation and tells the model how long ago it stopped, and that the desktop kept running without it. That matters more than it sounds: this is not a coding agent picking up files that are still where it left them — windows closed, somebody else may hold the controls, and the screen it remembers is a photograph.

Before spending anything

sentineldesk-agent -doctor                        # 15 checks against the real desktop, no model
sentineldesk-agent -tools "audit the firewall"    # what it would be offered, and its ranking
sentineldesk-agent -skills                        # the skills found, and where each came from
sentineldesk-agent -providers                     # which models can be reached, and what each needs

-doctor is the first thing to run when something is wrong. It talks to the real desktop, involves no model and costs nothing. If it fails, the problem is not the key.

Running it on the host instead

The agent finds the socket in the sentineldesk-run volume by itself, so it does not have to be in a container at all:

docker compose up -d sentineldesk   # the desktop only
sentineldesk-agent -serve           # the agent, on the host

This is the lightest way to work while you are changing the agent — no image to rebuild between edits. Do not run both: two runtimes on one desktop means the newer connection wins and the older is dropped. Nothing breaks; it is just confusing. Pick one.

What is installed, and the two images

Two variants come out of one build. Lite is the default; full adds what is too large or too specialised to hand everybody.

Lite here does not mean headless — on a Raspberry Pi that is what "Lite" means, but here the desktop is the product. It means the smallest set that leaves nobody reaching for a package manager on their first afternoon: a browser, a text editor, image and document viewers, an archive manager, a calculator and a task manager, plus the network toolbox this desktop mostly exists to use — nmap, dig, iperf3, tcpdump, mtr, sngrep and an OpenVPN client. Git is there too, because everybody clones something.

Full adds LibreOffice, Firefox, GIMP, Wireshark, a compiler toolchain and Go, and on Intel machines also Steam and Wine.

Go sits in full rather than lite deliberately, even though this project is written in it. A toolchain is a quarter of a gigabyte for people who will never type go, and "everybody clones something" is a claim that holds for git and not for a compiler.

Full contains lite

Full is built on top of lite rather than beside it, so everything in one is in the other. It also means the two share almost all their storage: a machine that already has lite downloads only the difference.

Finding things

The menu is grouped by what you want to do. Terminal, Web Browser, Files and Text Editor sit at the top because they are what gets opened every session; Accessories, Network and System Tools hold the rest, and All Applications lists everything installed.

The command-line entries under Network open a terminal with the tool's usage already printed, so you do not have to go and look up the flags first.

Connecting to a VPN

Network → VPN asks for a .ovpn profile and connects. Profiles kept in ~/.openvpn are offered directly, and the home survives restarts, so a connection you set up once stays set up.

This needs the container to have been started with a tunnel device and network privileges. If it was not, the dialog says so and shows the two lines to add rather than failing quietly.

Clock and keyboard

Both are set when the desktop starts, so one image serves every region. The clock follows TZ — any standard name such as America/Argentina/Buenos_Aires — and the keyboard follows KEYBOARD_LAYOUT: us, es for Spain, latam for Latin America, and so on.

If either is spelled wrong it is reported and ignored rather than half-applied. A clock quietly running in UTC because of a typo is worse than one that tells you.

When something is wrong

Nothing arrives at VLC

Almost always one of three things. Check them in this order:

  1. VLC is not actually listening. lsof -nP -iUDP:5000 must show UDP *:5000. A random high port means it is calling out, not listening — you forgot the @.
  2. The address points somewhere the container cannot reach. From inside Docker, localhost is the container itself, and a host address inside 172.17.0.0/16 collides with Docker's own bridge.
  3. You are using srt:// with VLC. See above.

The interface did not change after a rebuild

It should — the client is served with an ETag over its own bytes, so the browser has to revalidate. If it genuinely persists, confirm the container was recreated and not just restarted: make up rebuilds the image.

The picture is soft, or lagging behind

Open Statistics. It shows the live bitrate, frames, packets, how far behind live you are, and a clock down to milliseconds — which is the quickest way to tell whether two browsers are actually in sync.

Software encoding 1080p is the usual cause. Set ENCODER=x264 if auto-detection landed on VP8, and check whether the host has a GPU worth using with nvenc or vaapi.

Keys are not reaching the desktop

Check the presence panel: only the participant holding control sends input. If a window of the control layer is open, the keyboard belongs to it, not to the desktop.
